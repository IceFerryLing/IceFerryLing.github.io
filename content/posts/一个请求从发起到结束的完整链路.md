# vLLM 一个请求从发起到结束的完整链路

本文以 vLLM V1 的典型架构为背景，用一个请求的视角解释它如何从 HTTP 请求变成流式文本。不同 vLLM 版本的类名和文件路径可能变化，但整体分工和调用闭环基本一致。

## 1. 先建立全局认识

一次请求不是“调用一次模型函数”就结束，而是不断重复下面的循环：

```text
接收请求 → 分词 → 进入队列 → 调度一轮任务 → GPU 执行
        → 采样一个或多个 token → 更新状态 → 再次调度
```

直到请求遇到 EOS、stop 条件，或达到最大输出长度。

完整链路可以画成：

```text
Client
  ↓ HTTP
API Server
  ↓
Tokenizer / InputProcessor
  ↓
AsyncLLM / EngineClient
  ↓ IPC（常见为 ZMQ）
EngineCore
  ↓
Scheduler
  ↓ SchedulerOutput
Executor
  ↓
Worker
  ↓
ModelRunner
  ↓
模型前向 + Attention + KV Cache + Sampler
  ↓ ModelOutput
EngineCore 更新请求
  ↓
OutputProcessor / Detokenizer
  ↓ SSE 流式响应
Client
```

可以用一句话记忆各层职责：

> API Server 负责接入，Scheduler 负责决定，Executor 负责分发，Worker 负责管理 GPU，ModelRunner 负责计算，OutputProcessor 负责返回。

## 2. 客户端发送请求

客户端可能调用 OpenAI 兼容接口：

```json
{
  "model": "Qwen",
  "messages": [{"role": "user", "content": "介绍 KV Cache"}],
  "stream": true,
  "max_tokens": 128,
  "temperature": 0.7,
  "top_p": 0.9
}
```

`stream=true` 表示生成过程中就持续返回增量文本，不必等完整答案生成后再一次性返回。

## 3. API Server：把网络请求变成内部请求

入口通常在 `vllm/entrypoints/openai/api_server.py`。API Server 做参数解析、鉴权、模型名检查、请求 ID 分配和连接管理，但不直接执行 GPU 计算。

简化代码如下：

```python
async def create_completion(http_request):
    params = parse_request(http_request)
    request_id = make_request_id()

    async for output in engine_client.generate(
        request_id=request_id,
        prompt=params.prompt,
        sampling_params=params.sampling_params,
    ):
        yield format_as_sse(output)
```

此时请求仍然是“用户层请求”，还没有变成 GPU 可以直接使用的张量。

## 4. Tokenizer 和 InputProcessor：文本变成 token

模型不直接接收字符串，而接收整数 token ID。Tokenizer 会把文本切成 token：

```text
“介绍 KV Cache”
        ↓
[101, 2054, 893,  ...]
```

InputProcessor 还会整理模板、系统提示词、采样参数、停止条件和长度限制。内部请求可以抽象为：

```python
class EngineCoreRequest:
    request_id: str
    prompt_token_ids: list[int]
    output_token_ids: list[int]
    num_computed_tokens: int
    max_new_tokens: int
    sampling_params: SamplingParams
    status: RequestStatus
```

此时 `num_computed_tokens` 通常为 0，请求进入 Scheduler 的 `waiting` 队列。

## 5. 前端进程和 EngineCore 进程

典型部署会把接收网络请求的前端和真正驱动推理的 EngineCore 分开：

```text
API Server / AsyncLLM  ── IPC ──>  EngineCore  ──>  GPU Worker
```

这样网络连接、tokenize 和流式输出不会阻塞 GPU 推理循环。EngineClient 负责把内部请求送进 EngineCore，EngineCore 负责持续运行 `step()`。

## 6. EngineCore：系统的主循环

EngineCore 的核心不是一个只执行一次的函数，而是一个持续循环：

```python
while has_unfinished_requests():
    scheduler_output = scheduler.schedule()
    model_output = executor.execute_model(scheduler_output)
    request_outputs = scheduler.update(model_output)
    send_outputs_to_frontend(request_outputs)
```

每一轮都包含三个阶段：

1. `schedule`：决定这一轮计算谁、计算多少 token；
2. `execute`：让 GPU 真正完成模型前向和采样；
3. `update`：把新 token 写回请求状态，判断是否结束。

这就是 vLLM 的核心闭环。

## 7. Scheduler：调度的是 token 计算任务

Scheduler 类似操作系统里的调度器，但它调度的不是 CPU 线程，而是 LLM 请求的 token 计算。

它通常维护：

```text
waiting：尚未开始计算的请求
running：已经开始、正在生成的请求
swapped：资源不足而暂时暂停的请求
finished：已经完成、等待清理的请求
```

Scheduler 主要依据以下信息：

- 请求到达顺序（通常接近 FCFS）；
- prompt 还有多少 token 未计算；
- 本轮允许处理的 token 数量（token budget）；
- KV Cache 是否有足够的 block；
- 当前 batch 大小和序列长度限制；
- 是否启用 chunked prefill、抢占或优先级策略。

它不是简单 FIFO，也通常不会每轮直接读取 GPU 利用率再决定队列。它通过 token 预算、KV Cache 空间和队列状态，间接平衡吞吐量与延迟。

### 7.1 Prefill 和 Decode

Prefill 是第一次处理 prompt：一次计算较多输入 token，建立 KV Cache，通常偏 compute-bound。

Decode 是 prompt 已经处理后，每轮生成一个新 token：需要频繁读取 KV Cache，通常更偏显存带宽和延迟敏感。

因此一轮可能是：

```text
A：decode，处理 1 个 token
B：decode，处理 1 个 token
C：prefill，处理 128 个 token
```

真实实现未必保存一个简单的 `mode="prefill"` 字段，而是结合 `num_computed_tokens`、prompt 长度和 `num_scheduled_tokens` 推断执行阶段。

### 7.2 简化的调度代码

```python
def schedule(self):
    budget = self.max_num_scheduled_tokens
    tasks = []

    # 先让 running 请求继续 decode
    for req in self.running:
        if budget <= 0:
            break
        if not self.kv_cache.can_allocate(req, 1):
            self.preempt(req)
            continue

        self.kv_cache.allocate(req, 1)
        tasks.append((req.id, 1))
        budget -= 1

    # 再按等待顺序接纳新请求做 prefill
    while self.waiting and budget > 0:
        req = self.waiting[0]
        remaining = len(req.prompt_token_ids) - req.num_computed_tokens
        n = min(remaining, budget)

        if not self.kv_cache.can_allocate(req, n):
            break

        self.waiting.pop(0)
        self.running.append(req)
        self.kv_cache.allocate(req, n)
        tasks.append((req.id, n))
        budget -= n

    return SchedulerOutput(tasks)
```

这段代码只是帮助理解：真实 vLLM 还会处理 prefix caching、chunked prefill、抢占、结构化输出和多种 KV Cache 配置。

## 8. SchedulerOutput：从请求状态到执行描述

Scheduler 不直接调用模型，而是生成 `SchedulerOutput`。它描述本轮 GPU 要做什么：

```python
SchedulerOutput(
    scheduled_requests=[
        {"request_id": "A", "num_scheduled_tokens": 1,
         "block_table": [7, 12]},
        {"request_id": "B", "num_scheduled_tokens": 128,
         "block_table": [3, 8, 15]},
    ],
    finished_requests=[],
)
```

它包含的关键信息包括：请求 ID、本轮 token 数、序列长度、KV block 映射、位置索引所需信息，以及完成、抢占或换入换出信息。

## 9. KV Cache：调度必须考虑的资源

Transformer 的 Attention 会反复使用历史 token 的 Key 和 Value。vLLM 把这些结果保存为 KV Cache，避免 decode 时重算整个历史序列。

KV Cache 通常按固定大小 block 管理：

```text
请求的逻辑 block：[0, 1, 2]
          ↓ Block Table
实际物理 block：[7, 12, 19]
```

逻辑上连续、物理上可以不连续，类似操作系统的分页。Scheduler 在接纳请求前要确认 block 足够；请求结束后释放 block；如果资源紧张，还可能抢占请求并释放或换出其缓存。

## 10. Executor：把调度结果分发给 Worker

Executor 不负责选择请求，它负责执行层的组织：

```python
class Executor:
    def execute_model(self, scheduler_output):
        return self.worker.execute_model(scheduler_output)
```

单卡时可能只有一个 Worker；多卡时会有多个 Worker：

```text
Executor
  ├── Worker rank 0 → GPU 0
  ├── Worker rank 1 → GPU 1
  └── Worker rank 2 → GPU 2
```

Tensor Parallel、Pipeline Parallel 等并行方式主要在 Executor、Worker 和通信层协调。

## 11. Worker：每张 GPU 的管理者

Worker 通常持有模型、设备上下文、本卡 KV Cache 和 ModelRunner。它把任务交给 ModelRunner：

```python
class Worker:
    def execute_model(self, scheduler_output):
        return self.model_runner.execute_model(scheduler_output)
```

因此可以这样区分：Scheduler 决定“谁上车”，Worker 管理“哪张 GPU 开车”。

## 12. ModelRunner：把任务变成 GPU 张量

ModelRunner 是真正接近模型计算的模块。它读取 SchedulerOutput，准备本轮的输入张量和 Attention 元数据：

```python
def execute_model(self, output):
    input_ids = self.prepare_input_ids(output)
    positions = self.prepare_positions(output)
    attn_meta = self.prepare_attention_metadata(output)

    logits = self.model(
        input_ids=input_ids,
        positions=positions,
        attn_metadata=attn_meta,
    )
    next_tokens = self.sampler(logits)
    return ModelOutput(next_token_ids=next_tokens)
```

准备内容通常包括 `input_ids`、`position_ids`、`slot_mapping`、`block_table`、序列长度和 attention metadata。

Prefill 时，`input_ids` 可能包含一段尚未计算的 prompt token；Decode 时，通常只有新 token，但会通过 block table 读取完整历史 KV Cache。

## 13. 模型前向、Attention 和采样

模型内部大致经过 Embedding、多个 Transformer Block、Attention、MLP 或 MoE，最后得到 logits：

```text
input_ids → Embedding → Transformer Blocks → logits
```

Attention 后端根据元数据读取和写入 KV Cache，并调用 FlashAttention、FlashInfer 或 PagedAttention 等 kernel。Sampler 再根据 logits 和 temperature、top-p、top-k 等参数选择下一个 token ID。

```python
next_token_id = sampler(
    logits,
    temperature=0.7,
    top_p=0.9,
)
```

## 14. 结果返回 EngineCore 并更新状态

ModelRunner 返回 `ModelOutput` 后，EngineCore 要把 token 写回对应请求：

```python
def update(self, model_output):
    for item in model_output:
        req = self.requests[item.request_id]
        req.output_token_ids.append(item.token_id)
        req.num_computed_tokens += 1

        if is_finished(req, item):
            req.status = FINISHED
            self.kv_cache_manager.free(req)
        else:
            req.status = RUNNING
```

未完成的请求继续留在 `running`，下一轮再次进行 decode；完成的请求释放 KV Cache，等待输出完成信号。

## 15. Detokenizer 和流式输出

生成 token ID 后，OutputProcessor 负责增量解码并组装 SSE：

```text
token_id 5021
    ↓
Detokenizer
    ↓
“KV”
    ↓
SSE 增量消息
    ↓
客户端屏幕
```

用户看到的文字并不是模型直接产生的，而是 token ID 经 Detokenizer 转换后的结果。

## 16. 一个请求的具体时间线

假设请求 A 的 prompt 有 4 个 token，需要生成 3 个 token：

```text
第 1 轮：A prefill 4 个 prompt token，建立 KV Cache，生成 A1
第 2 轮：A decode 1 个 token，读取 KV Cache，生成 A2
第 3 轮：A decode 1 个 token，读取 KV Cache，生成 A3
第 4 轮：遇到 EOS 或达到限制，释放 KV Cache，返回完成信号
```

如果请求 B 在第 2 轮到达，continuous batching 可能产生：

```text
第 2 轮：A decode 1 token + B prefill 128 token
第 3 轮：A decode 1 token + B decode 1 token
```

每一轮 batch 都可能变化，因此它不是固定批处理。

## 17. 调度策略的准确理解

常见默认思路可以概括为：

```text
FCFS 倾向
+ running 请求持续 decode
+ waiting 请求按顺序尝试 prefill
+ token budget 限制
+ KV Cache 资源限制
+ 必要时抢占、暂停和恢复
```

它的目标是在 decode 延迟和整体吞吐之间取得平衡。通常不是实时读取“哪个 GPU 利用率低”再直接补任务，而是用可预测的 token 预算和内存状态来调度。生产环境可以通过配置、监控和外部路由器进一步做负载优化。

## 18. 可以接入哪些外部系统

### 18.1 Mooncake：分布式 KV Cache

Mooncake 更适合接在 KV Cache 管理和传输层，而不是替换 Scheduler：

```text
KVCacheManager
      ↓
本地 GPU KV Cache
      ↓
Mooncake 分布式 KV Cache
      ↓
其他 GPU / CPU / 内存节点
```

典型接口可以抽象为：

```python
class ExternalKVConnector:
    def lookup(self, prefix_hash): ...
    def load(self, blocks): ...
    def store(self, blocks): ...
    def evict(self, blocks): ...
```

请求进入时可以先计算 prompt 前缀的 hash，查询 Mooncake：命中则加载已有 KV，减少 prefill；未命中则本地计算，之后把新 KV 写回远端。

接入 Mooncake 需要让调度层知道哪些 token 已经被远端缓存恢复，哪些仍需本地计算。因此通常是扩展 KV Cache Manager、Connector 和 ModelRunner 的加载路径，Scheduler 只做必要的状态配合。

### 18.2 DeepEP：MoE Expert Parallel 通信

DeepEP 主要位于 MoE 执行和跨 GPU 通信层：

```text
ModelRunner
  ↓
MoE Layer / Router
  ↓
DeepEP Dispatch
  ↓
远程 Expert
  ↓
DeepEP Combine
```

Router 决定 token 去哪个 Expert，DeepEP 负责高效的 token dispatch/combine 和 All-to-All 通信。它通常不要求替换 Scheduler，而是在 ModelRunner、MoE Runner、Expert Parallel 和通信后端附近接入。只有当通信对 batch 形状有特殊要求时，才需要向 Scheduler 增加元数据或约束。

### 18.3 Attention 后端

FlashAttention、FlashInfer 等通常接在：

```text
ModelRunner → Attention Layer → AttentionBackend → Kernel
```

Scheduler 提供序列长度、block table、slot mapping 和 attention metadata，具体 kernel 由 AttentionBackend 选择。

### 18.4 PD（Prefill-Decode）分离

PD 分离通常需要把资源拆成两类实例：

```text
Router
  ├── Prefill Worker 集群
  └── Decode Worker 集群
```

这不仅是替换 Scheduler，还要解决 KV Cache 从 prefill 实例传给 decode 实例、请求状态跨实例同步和两类资源路由等问题。Scheduler 可能被扩展为跨实例调度器，但 vLLM 单实例内的基本调度逻辑仍然存在。

## 19. 推荐的源码阅读顺序

建议始终围绕一个请求追踪两个对象：

```text
Request：请求当前处于什么状态？
Batch：这一轮 GPU 实际要算什么？
```

源码阅读顺序可以是：

```text
vllm/entrypoints/openai/api_server.py
vllm/v1/engine/async_llm.py
vllm/v1/engine/core.py
vllm/v1/core/sched/scheduler.py
vllm/v1/core/kv_cache_manager.py
vllm/v1/core/block_pool.py
vllm/v1/executor/
vllm/v1/worker/gpu_model_runner.py
vllm/attention/backends/
```

不同版本可能把路径改为 `vllm/v1/core/sched/` 或调整类名，实际阅读应以本地版本为准。

## 20. 最终总结

一个请求的完整闭环是：

```python
request = api_server.receive()
tokens = tokenizer.encode(request.prompt)
engine.add_request(tokens)

while not request.finished:
    task = scheduler.schedule()
    result = model_runner.execute(task)
    scheduler.update(result)
    stream_to_client(result)

free_kv_cache(request)
```

真正需要记住的是每层边界：

> Scheduler 决定“谁算、算多少”；ModelRunner 决定“如何把它算出来”；KV Cache 负责保存历史状态；OutputProcessor 负责把 token 变回用户看到的文字。

Mooncake、DeepEP、FlashAttention 等组件通常分别接入 KV Cache、MoE 通信和 Attention kernel 层。它们是在特定环节替换或扩展实现，而不是把整个 vLLM 请求链路推倒重来。
